# Rhombiverse — Dimensional Construction Interface

**Author:** DICTO (Alan J. Baker) · **Project:** Rhombiverse · **Concept development record:** 2026-09-28 · **Status:** Concept / implementation planning

---

## 1. Core Concept

The 1D mode is not simply a visualization of a line.

It is a **construction microscope**: a way to enter the smallest structural unit, travel through it, fill it, encounter junctions, and progressively reveal how higher-dimensional primitives and lattices are composed.

The central progression is:

```
1D cell → axis → parallel axes → junction → primitive → lattice
```

The crucial distinction is that these terms describe different things:

- **Cell** = an elementary 1D unit or interval.
- **Axis direction** = a dimensional direction such as X, Y, Z, W, V or U.
- **Axis instance** = a particular line/axis occupying a location in the construction.
- **Parallel axes** = distinct axis instances sharing the same direction.
- **Junction** = a location where another construction relationship or axis direction can become available.
- **Primitive** = the dimensional form emerging from the organized cells and axes.
- **Lattice** = the larger environment generated by repeated relationships between primitives.

A cell is therefore not an axis, and a collection of cells along an axis is not itself a collection of different axes.

## 2. The Fundamental Unit: The 1D Cell

The elementary cell is the smallest unit encountered by the user.

A 1D construction may contain many sequential cells along one axis.

```
X → X → X → X → …
```

The number of units is not limited to a few subdivisions. A useful construction may contain ten, dozens, or more units along each relevant direction.

The cells may initially be geometrically present but unfilled.

### Cell states

- **Unfilled:** geometrically available but not yet part of the user's active construction.
- **Filled:** actively constructed and visually encoded.
- **Unavailable:** not accessible under the current dimensional/structural conditions.

This makes filling a meaningful act of construction rather than merely revealing a pre-rendered object.

## 3. Axis Direction vs Axis Instance

This distinction is fundamental.

### Axis direction

A dimensional coordinate direction: X, Y, Z, W, V, U.

### Axis instance

A particular line occupying a position in the structure.

Several lines can all be parallel to X. They share the X direction but occupy different positions. For example:

```
X-directed axis A:  •—•—•—•—•—•—•—•—•—•
X-directed axis B:  •—•—•—•—•—•—•—•—•—•
X-directed axis C:  •—•—•—•—•—•—•—•—•—•
```

Each line contains many cells; the lines themselves are parallel axis instances.

The interface therefore needs separate internal concepts for:

```
cell ≠ axis direction ≠ axis instance
```

This distinction should be preserved in both the data model and the terminology presented to the user.

## 4. Building a Dimension from 1D Units

The construction should not begin with a finished cube, hypercube or other primitive and merely subdivide it.

Instead, the user should be able to understand the higher-dimensional structure as emerging from repeated 1D units and their relationships.

For a simple 3D example:

**1D** — a sequence of cells along X:

```
X → X → X → X → …
```

**2D** — additional parallel X-directed axes are organized through a Y relationship. Conceptually:

```
X-directed cells + Y relationship → 2D field/primitive
```

**3D** — the resulting 2D organization is extended through Z:

```
X + Y + Z → 3D primitive
```

Thus:

```
1D units → organized parallel axes → dimensional field → primitive
```

The exact construction must be defined for each mathematical object; the interface should not imply that every higher-dimensional structure follows an identical construction rule.

## 5. Junctions: Exposing, Not Replacing, Axes

A junction should not be understood as a point where one axis is simply changed into another.

The important rule is:

> **An axis is not replaced at a junction; another axis relationship becomes available.**

For example, `X → junction → Y` means that the construction has encountered a relationship through which Y can now participate. It does not mean that X has ceased to exist.

Likewise, `X + Y → junction → Z` means Z becomes available to extend the existing construction.

This is especially important when many parallel axes are present. A junction may therefore connect:

- cells on the same axis instance;
- one parallel axis instance to another;
- or an existing construction to a newly available dimensional direction.

The precise topology depends on the primitive or lattice being constructed.

## 6. Two Complementary 1D Experiences

### 6.1 Explore 1D itself

The user enters a navigable 1D environment composed of elongated cell/tunnel units.

Possible characteristics:

- Long, bullet-like or capsule-like cells.
- Sequential cells forming the 1D structure.
- Travel through the cells along the relevant axis.
- Ability to view the structure from above/below or other controlled viewpoints while retaining the mathematical interpretation as 1D.
- Cells remain the fundamental structural units.

The goal is to make 1D something the user can experience, rather than merely see represented as a line.

### 6.2 Use 1D as the construction microscope

The same elementary cells become the units through which higher-dimensional structures are revealed.

The user can progress through `1D → 2D → 3D → 4D → 5D → 6D → …` without implying that 1D itself has acquired additional dimensions. Instead, additional axis relationships become available through which the 1D units are organized.

## 7. Traversal vs Construction

These are related but distinct activities.

- **Traversal** — the user travels through cells and along axis instances that already exist in the current environment. Traversal answers: *Where can I go?*
- **Construction** — the user fills cells and activates valid relationships so that a primitive or larger structure emerges. Construction answers: *What am I building, and how is it composed?*

A journey through a cube should therefore not be interpreted simply as a path around a finished cube. The user can instead experience the underlying construction grammar:

```
cell → repeated cells → parallel axis instances → junction → additional axis relationship → primitive
```

This separation should be reflected in the implementation so that exploration does not accidentally imply that traversal itself is the mathematical construction.

## 8. Primitive-First Construction

The preferred progression remains:

```
1D cells → dimensional primitive → lattice
```

rather than immediately revealing the entire lattice. The primitive should emerge from the construction process before the larger environment is revealed.

Examples of related dimensional families to explore include:

- Square → Cube → Hypercube
- Kagome 2D → Kagome 3D → higher-dimensional relatives where mathematically appropriate
- Pentagon → Dodecahedron → 4D dodecahedral relatives
- Other corresponding primitive/lattice families already represented in Rhombiverse

The exact mathematical relationships must be verified individually rather than assumed from visual similarity.

## 9. Progressive Filling

Filling is an active construction state. A typical experience might begin with neutral potential cells:

```
○—○—○—○—○—○—○—○—○—○
```

As the user constructs:

```
●—●—●—●—○—○—○—○—○—○
```

the filled portion records progress.

When another axis becomes available, the user can begin filling cells along the corresponding construction relationship.

The result is not simply a colored version of a finished object. The object progressively emerges through the filling process.

The system should preserve the distinction between:

- the mathematical existence of a cell;
- the user's current construction state;
- the geometry that eventually emerges from those states.

## 10. Primitive Emergence

A key experiential goal is:

> **The primitive is not merely presented; it emerges from the accumulation and organization of 1D cells.**

For example, a cube may be encountered through a sequence in which:

1. X-directed cells are filled.
2. Additional parallel X-directed axes become relevant.
3. Y relationships organize those parallel X-directed axes.
4. The resulting 2D organization is extended through Z.
5. The completed organization resolves as a cube.

The exact number, topology and ordering of cells must follow the actual geometry of the selected primitive.

The interface should therefore support **construction rules per mathematical object**, rather than imposing one universal algorithm on every shape.

## 11. Axis/Junction Interface Language

Dimensional axes become part of the geometry's own interface.

Suggested axis sequence: X, Y, Z, W, V, U.

A junction can expose available axis directions as selectable relationships.

The interface should distinguish:

- the direction being represented;
- the particular parallel axis instance involved;
- the cell currently being traversed or filled.

### Availability states

- **Active:** fully visible and interactive.
- **Available but secondary:** visible/faint.
- **Unavailable:** faded and inaccessible.

The system should avoid presenting all possible axes as if they were simultaneously active.

## 12. 1D X / 1D Y Viewing Relationship

The 1D experience may support a toggle between two complementary viewing/following relationships, provisionally described as **1D X** and **1D Y**.

This must not imply two mathematical dimensions within a 1D object. It represents a relationship between the 1D construction and the direction being examined.

When a higher-dimensional structure is being explored, the currently relevant axis can be emphasized while other axis relationships remain faded or inaccessible.

The terminology should be tested carefully so that 1D X / 1D Y cannot be mistaken for claiming that a single 1D object possesses both X and Y dimensions simultaneously.

## 13. Axis-Based Colour Provenance

Each axis direction should have a persistent colour identity or palette.

Illustrative mapping:

| Axis direction | Role |
| --- | --- |
| X | primary direction |
| Y | second direction |
| Z | third direction |
| W | fourth direction |
| V | fifth direction |
| U | sixth direction |

The important principle is:

> **Colour represents dimensional provenance, not decoration.**

A filled cell can therefore carry the colour associated with the axis relationship through which it was constructed. This lets users see construction history while keeping the cell's geometric identity separate from its visual encoding.

## 14. "Same Animal, Different Zoo"

A major conceptual goal is to let users recognize related primitives across dimensions.

The metaphor is:

> **The primitive is the animal; the dimensional lattice is the zoo.**

The user encounters structurally related forms in different dimensional environments. Examples include:

- Square → Cube → Hypercube
- Kagome 2D → Kagome 3D → higher-dimensional counterparts (potentially)
- Pentagon → Dodecahedron → 4D dodecahedral relatives

The interface should make the relationship discoverable rather than asserting that superficially similar objects are mathematically identical.

## 15. Dimensional Progression

The system should avoid presenting every possible axis at once. Conceptually:

```
1D: X
2D: X + Y
3D: X + Y + Z
4D: X + Y + Z + W
5D: X + Y + Z + W + V
6D: X + Y + Z + W + V + U
```

This describes **available axis directions**, not the number of individual parallel axes or cells. For example, a 3D cube may contain many parallel X-directed axis instances, many parallel Y-directed instances and many parallel Z-directed instances.

Higher dimensions beyond 6D should remain architecturally possible rather than hard-coded as an endpoint.

## 16. Interface Principles

The feature should preserve Rhombiverse's simplicity-first philosophy. Prefer:

- symbols over explanatory words;
- direct manipulation over menus;
- geometry as interface;
- progressive disclosure;
- few controls;
- persistent visual language;
- inactive dimensions visibly faded;
- clear distinction between cell, axis and junction;
- no unnecessary control duplication.

The dimensional system should teach through interaction.

## 17. Mathematical Integrity

The visualization must distinguish:

1. established mathematical objects;
2. established visualization/projection techniques;
3. Rhombiverse's own interface and construction concepts.

The system should use precise terminology:

- **cell** for an elementary unit;
- **axis direction** for X/Y/Z/W/V/U;
- **axis instance** for a particular line in that direction;
- **parallel axes** for distinct instances sharing the same direction;
- **junction** for a structural connection where another relationship may become available.

Where a higher-dimensional analogue or family relationship is uncertain, it should be mathematically verified before being presented as a correspondence.

The feature should not imply that a visual resemblance establishes mathematical equivalence.

## 18. Suggested Implementation Architecture

Separate the feature into layers.

### Geometry layer

Defines: cells; axis directions; axis instances; parallel-axis relationships; junctions; primitives; lattice relationships.

### Dimensional relationship layer

Defines:

- which axis directions are valid;
- which parallel-axis relationships exist;
- which junction transitions are valid;
- which construction stages belong to each dimensional structure.

### Construction layer

Generates primitive and lattice structures from lower-level cells and relationships. This layer should support filling and progressive construction rather than assuming the final object already exists.

### View/navigation layer

Handles:

- travel through cells;
- following an axis instance;
- crossing junctions;
- switching viewing relationships;
- progressive reveal.

### Visual encoding layer

Maps:

- axis directions to persistent palette identities;
- construction states to filled/unfilled appearance;
- availability to active/faded states.

### Interaction layer

Handles:

- symbolic axis/junction selection;
- cell filling;
- Explore/Build transitions;
- dimensional progression.

This separation should allow the same underlying construction logic to support 2D through higher dimensions.

## 19. Prototype Sequence

A sensible first implementation would be:

1. Build the navigable 1D cell/tunnel.
2. Implement multiple sequential cells along a single X-directed axis.
3. Establish the distinction between cell, axis direction and axis instance in the data model.
4. Implement X-axis cell filling.
5. Add additional parallel X-axis instances.
6. Add junctions between appropriate axis instances.
7. Introduce Y as a new axis direction without replacing X.
8. Construct a simple 2D primitive from the resulting relationships.
9. Add axis palette encoding to filled cells.
10. Extend the same mechanism into a 3D primitive by introducing Z.
11. Test the primitive → lattice transition.
12. Test traversal independently from construction.
13. Experiment with 4D using W.
14. Validate the interaction architecture before extending to 5D/6D.
15. Integrate with existing Rhombiverse dimensional structures.
16. Document each major conceptual and implementation milestone.

## 20. Conceptual Example: Cube

A simplified cube construction can be used as the first proof-of-concept.

**Initial state** — one X-directed axis containing many unfilled 1D cells:

```
○—○—○—○—○—○—○—○—○—○
```

**X construction** — cells are filled sequentially along X.

**Parallel X structure** — additional X-directed axis instances become part of the construction. They are still X-directed; they are not new dimensions.

**Y relationship** — at appropriate junctions, Y becomes available to connect or organize the parallel X-directed axes. The construction now has `X direction + Y direction` and can form a 2D primitive.

**Z relationship** — the resulting 2D organization is extended through Z. The construction now has `X direction + Y direction + Z direction` and can resolve as a 3D cube.

The important point is that the cube is understood as the result of organized 1D units and axis relationships, not as a pre-existing cube that happens to have been divided into cells.

## 21. Success Criterion

The feature succeeds if a user can encounter a higher-dimensional structure and understand, through direct interaction:

- What is the elementary cell?
- Which axis direction does it belong to?
- Which parallel axis instance am I on?
- What happens at the junction?
- Which new axis relationship becomes available?
- How do the filled cells compose the primitive?
- How does the primitive participate in the larger lattice?
- How does the same structural idea change as dimensionality increases?

The goal is not merely to make higher dimensions visible. It is to make their construction and composition experientially understandable.

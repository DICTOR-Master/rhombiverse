# Rhombiverse — Spec Addendum: Recursive Lattice Detail (Lattice Zoom)

Standalone addendum, drafted from a live design discussion (2026-08-13),
not implemented yet. Complies with `RHOMBIVERSE_PRINCIPLES.md` — Grounded
Simplicity, Isolation, Adaptive Damping are called out explicitly below.

## 0. The idea, in one paragraph

Right now every RD cell is a fixed-size primitive: it looks the same
whether the camera is a kilometer away or right next to it, and only the
*count* of visible cells changes with distance. This spec makes the
lattice itself reveal structure as the camera approaches — a cell that
reads as one solid block from afar turns out, up close, to be built from
a smaller cluster of RD cells packed the same way. Continuous-feeling
zoom (like a camera racking focus between a wide shot and a close-up),
not a discrete mode switch.

Governing decisions (confirmed with the project owner in the discussion
that produced this draft):

1. **Base RD lattice, gameplay-relevant** — this is about the actual
   world lattice, not a cosmetic surface-detail effect layered on top of
   otherwise-unchanged geometry.
2. **Continuous zoom, not a discrete mode** — no "enter close-up mode"
   button; detail resolves as the camera gets closer, the way focus pulls
   in a real lens.
3. **Uniform substructure, for this pass** — a cell's revealed
   sub-lattice always follows the same recursive packing pattern; it does
   not (yet) hide unique/procedural content per cell. Explicitly left open
   for a later pass, not precluded by this one.
4. **Building/mining stays at block level, for this pass.** The recursive
   detail is real geometry a player perceives as part of the world, not a
   fake shader trick — but it is not independently buildable/mineable
   yet. A later wave ("a more rendered approach could interact with and
   change the close-up view," the project owner's own framing) is where
   sub-scale interactivity would go — not scoped here.
5. **Close-up view also surfaces the ecosystem, at two tiers.** A few
   real, individually-tracked organisms (`RHOMBIVERSE_SPEC_EVOLUTION_
   ECOSYSTEM.md`'s own `organisms` registry — real genomes, real growth
   history) render as themselves; everything else reads as a broader
   aggregate/general visual layer driven by that same real population's
   stats (coverage percentage, dominant trait values, species mix), not
   independently simulated per visible instance. See section 6.

## 1. Grounded Simplicity: this is not invented geometry

The RD is already this project's own Voronoi cell of the FCC lattice
(`lattice.js`'s own header). Real crystalline materials are genuinely
self-similar across scale this way — the same close-packing arrangement
recurs from the unit-cell scale up through visible crystallite grains,
not a metaphor borrowed for this game but the actual physics the game's
own lattice is already modeled on. That means "zoom into a block and it
turns out to be built from smaller RD-packed blocks" requires no new
geometry system: it's `lattice.js`'s own `NEIGHBOR_OFFSETS`/
`cellsInShells`/`shellCount(n) = 10n²+2` math, reused at a smaller nested
scale inside each cell, exactly the same "implement once, import
everywhere" discipline CLAUDE.md already holds every other subsystem to.

A parent cell's sub-lattice is generated by treating the parent cell's
own center as a new local origin, running `cellsInShells` outward some
small number of shells, and scaling the result down by a
`SUB_SCALE_FACTOR` chosen so the sub-cells' own Voronoi volumes
approximately tile the parent cell's real volume — the real geometric
relationship to verify during implementation (per this project's own
"verify against the real generator output, not guessed here" convention
for exactly this class of constant), not fixed by this draft.

## 2. Bounded Depth (not infinite recursion)

Even "continuous" zoom in real engines is built from a handful of
discrete detail levels with smooth blending between them, not unbounded
per-frame geometric subdivision — no real renderer, with or without a
build step, computes truly infinite recursive detail live. `MAX_LOD_DEPTH`
bounds how many nested levels exist (a real, tunable number — 2 or 3 is
the likely practical range, verified during implementation against actual
frame cost), matching this project's own established pattern of every
other potentially-unbounded system (`MAX_CATCHUP_GENERATIONS`,
`MAX_CLAIM_SEARCH_SHELL`, `MAX_CELLS`, `MAX_GENERATED_CELLS`, `MAX_UNDO`)
— a real cap grounded in measured cost, not an arbitrary-feeling limit.
The zoom still *feels* continuous through cross-fade/scale blending
between levels as the camera crosses each threshold, same as how real
LOD systems achieve a smooth-reading transition from discrete underlying
levels.

## 3. Trigger & Lifecycle (reuse existing patterns, not new tech)

Camera-distance-driven: cells within a threshold distance of the camera
become candidates for their sub-lattice to be built and shown; cells that
fall back out of range have that sub-lattice geometry disposed. This
reuses the exact lifecycle pattern `refreshClaims()` and
`rebuildSeedMeshes()`/`rebuildAllGrowth()` already use elsewhere in
`render.js` — clear-and-rebuild a dedicated group/mesh set on a
recompute trigger — rather than inventing a new rendering technique.
Sub-lattice geometry for near cells is a separate `InstancedMesh` (or
small set of them, one per LOD depth), built the same way the top-level
cell `InstancedMesh` already is (`buildRDGeometry`/`rdRawVerts`, scaled
down per level) — no shader/compute-pipeline work required to ship a
first version, consistent with this project's own "no build step, by
design" principle: everything here is achievable in plain ES modules
against the CDN-loaded Three.js already in use.

Recompute is triggered on camera movement, throttled (not every frame) —
the same "expensive operation, cheap gate" shape this project already
uses elsewhere (e.g. growth ticks on a periodic interval rather than
every frame).

## 4. Isolation (Blast Radius)

**Blast radius: near-camera only, purely additive to rendering.** Only
cells within the LOD trigger distance of the camera ever have sub-lattice
geometry computed, so cost is bounded by "how much is near the camera,"
never by total world size — the same shape as every other bounded system
in this project. Building/mining staying at block level (governing
decision 4) means this entire spec, for this pass, touches **no**
existing gameplay data model: not `worldstate.js`'s cell schema, not
inventory, not gravity mass, not claims, not the asteroid/trade economy.
It is a rendering-layer addition read against the existing `cells` map,
same as how claim visualization or growth-tile rendering already read
world state without owning any of it. A LOD bug can make the wrong
picture; it cannot desync or corrupt the real, synced game state.

## 5. Adaptive Damping

Rapid camera zoom in/out (a player scrubbing distance quickly) could
otherwise thrash the recompute/dispose cycle. Applies the same
generalized volatility-response shape `RHOMBIVERSE_PRINCIPLES.md` §2
already specifies elsewhere in this project (e.g. asteroid population
spawning, black hole generation cost): repeated rapid LOD-recompute
triggers within a short window widen the recompute throttle interval
(costlier to keep re-triggering), decaying back to the tight default
during calm, slow camera movement — so a player waving the camera around
never produces runaway rebuild cost, without needing a separate
special-cased threshold just for this system.

## 6. Ecosystem & Landscape Rendering (Real Organisms + Aggregate Layers)

The payoff for zooming in isn't just smaller blocks — per the project
owner's own framing, it's seeing the living landscape: plant life at its
true (miniscule, relative to a block) scale, reflecting real population
coverage and real evolutionary state, AND the landscape's own surface
features aggregating and changing the same way, not a decorative effect
bolted on separately from `RHOMBIVERSE_SPEC_EVOLUTION_ECOSYSTEM.md`'s own
simulation.

### 6.1 Two tiers (organisms), confirmed with the project owner — not
everything individually simulated

- **A few real organisms.** Whatever `evolution.js`'s own `organisms`
  registry actually tracks for the nearby area (real genome, real
  generation, real `growth.js` tiles) renders as an actual grown
  structure, at the correspondingly small visual scale a real organism
  should read at next to a full RD block — the exact scale-mismatch
  problem the project owner raised earlier in this same discussion,
  resolved by this spec's own LOD system rather than a separate scale
  hack: an organism is just more content that becomes visible once the
  camera is close enough for its actual (tiny) size to register at all.
- **Aggregate/general layer.** Everything else reads as a broader,
  lighter-weight visual layer — NOT independently tracked genomes/growth
  histories, but derived from the real tracked population's own
  aggregate outputs: local coverage percentage (reusing
  `RHOMBIVERSE_SPEC_EVOLUTION_ECOSYSTEM.md` section 5's own `biomass`
  figure once Evolution Stage 5 exists, as the natural existing source
  for "how much life is here" rather than a new metric invented here),
  and dominant/average trait values (branching angle, species mix) from
  the real nearby organisms, so the aggregate layer visually trends the
  same direction real evolution is actually moving a population —
  including making section 5.1's convergent-evolution check ("similarly-
  conditioned planetoids trend toward similar trait values") something a
  player can literally SEE from orbit-to-ground-level zoom, not just
  read in an inspect-tool number.

### 6.2 Landscape is also an aggregate — and a real, revisitable space

Not just plant coverage: the landscape's own surface features (surface
weathering, soil/sediment buildup, exposed-mineral patterns) are a
second aggregate layer, same rendering CLASS as 6.1's plant layer
(statistics-driven density/variation, not a uniquely-authored texture
per cell) — but grounded in a different, equally real mechanism: real
landscapes are visibly shaped by sustained biological presence over
time (root systems breaking down rock, moss/lichen colonization altering
weathering patterns, organic matter building soil) — this is the
existing "amoeba boosts nearby plant growth" symbiotic-coupling idea
(`RHOMBIVERSE_SPEC_EVOLUTION_ECOSYSTEM.md` section 5) extended one step
further, biology visibly reshaping substrate, not just other biology.

Critically — per direct correction during this discussion — this is a
**real, revisitable SPACE**, not a live-recomputed decoration: a
specific location's landscape-aggregate state persists and evolves while
unobserved, so a player who leaves and returns later finds that place
genuinely changed, reflecting real elapsed time and whatever evolutionary
activity happened there — the exact same shape as
`RHOMBIVERSE_SPEC_EVOLUTION_ECOSYSTEM.md` section 4's own deterministic
catch-up engine (`lastSimulated`/seeded RNG, resolved on load, bounded by
`MAX_CATCHUP_GENERATIONS`), reused rather than reinvented: landscape-
aggregate state is planetoid-scoped tracked data (a real, minimal new
field — NOT purely derived/read-only the way 6.1's organism rendering
is, flagged honestly since it breaks this spec's otherwise "rendering
only, owns nothing" pattern) that advances through the same bounded
catch-up resolution as organism generations do, influenced by nearby
real biomass/organism history as its input.

### 6.3 Isolation

**6.1 (organism rendering):** same standard as section 4 above — reads
`organisms`/`seeds`/biomass state Evolution's own stages already own and
compute, introduces no new simulated state, cannot desync from the real
ecosystem. A rendering bug here can show the wrong picture; it cannot
corrupt the ecosystem itself.

**6.2 (landscape aggregate state):** planetoid-scoped, same blast radius
as every Evolution mechanism (`RHOMBIVERSE_SPEC_EVOLUTION_ECOSYSTEM.md`
section 6) — a landscape-state runaway or reset bug on one planetoid
cannot affect another's. Bounded by the same `MAX_CATCHUP_GENERATIONS`-
style cap so a long-unvisited location resolves in bounded time on
return, never a real-time-proportional catch-up.

**Explicitly deferred:** procedural/unique per-cell aggregate content in
either layer (both are statistics-driven density/trend visualizations of
real tracked state, not their own generative systems); interactivity
with either aggregate layer (matches governing decision 4 — block-level
building only, for now).

## 7. Success Checks

- [ ] A cell far from the camera renders as a single solid block, no
      sub-lattice geometry computed for it.
- [ ] The same cell, approached closely, reveals a smaller-scale cluster
      of RD cells packed via the same lattice math, not new/different
      geometry.
- [ ] The transition reads as continuous (blended), not a hard pop, when
      crossing an LOD threshold at ordinary movement speed.
- [ ] Recursion never exceeds `MAX_LOD_DEPTH` regardless of how close the
      camera gets.
- [ ] Sub-lattice geometry for cells that fall back out of range is
      disposed, not accumulated (bounded memory over a long play
      session).
- [ ] Clicking/building/mining behavior is unchanged — every existing
      Build/Fill/Generate/Round/Excavate/Report/Plant mode still targets
      the top-level block exactly as it does today, regardless of current
      zoom level.
- [ ] Rapid repeated zoom in/out measurably widens the recompute
      throttle interval versus slow/calm camera movement (adaptive
      damping working).
- [ ] No existing gameplay data (`cells`, claims, inventory, gravity)
      changes shape or values as a result of this system existing.
- [ ] A real tracked organism near the camera renders as itself, at a
      scale correctly small relative to a full RD block, once close
      enough for the LOD system to reveal it.
- [ ] The plant-coverage aggregate layer's density/trend visibly reflects
      the real nearby population's own stats (coverage, dominant traits)
      — changing the real population measurably changes what the
      aggregate layer shows.
- [ ] A location's landscape-aggregate state (6.2) persists and evolves
      while unvisited — leaving, letting time/evolution pass elsewhere,
      and returning shows genuine accumulated change at that specific
      place, resolved in bounded time regardless of real elapsed time
      (reuses `MAX_CATCHUP_GENERATIONS`-style bounding).
- [ ] A landscape-state runaway or reset on one planetoid has zero
      measurable effect on another's (Isolation holds for 6.2 the same
      way it does for every Evolution mechanism).

## 8. Build Order

**Stage 1 — Static Sub-Lattice Geometry (no camera trigger yet) — DONE,
2026-08-13.** Given one specific cell, generate and render its sub-lattice
at a fixed test distance/scale, hardcoded, no LOD trigger logic. Verify the
sub-cells' own packing is geometrically correct (real FCC adjacency,
scaled) and their combined volume approximately tiles the parent cell,
before any camera-driven logic exists.

New `src/latticezoom.js`, reusing `lattice.js`'s own `cellsInShells`/
`shellCount`/`cellToWorld` directly (no new geometry system). `SUB_SCALE_
FACTOR` (`subScaleFactor(maxShell) = cbrt(1 / cumulativeCellCount(maxShell))`)
is not guessed: the RD's own volume at scale 1 was verified numerically
at exactly 2 (a real `ConvexGeometry` volume computation, 12 tetrahedra
fanned from the origin, summed — independently cross-checked against the
clean analytic argument that valid cells are exactly half of `Z^3`, so
Voronoi volume = 1/density = 2, both methods agreeing). This makes the
volume-conservation identity (`cellCount * factor^3 == 1`) exact, not
approximate — verified in `tests/unit/latticezoom.test.mjs` (7 tests) —
since Voronoi cells tile with zero gap/overlap by construction.
`SUB_LATTICE_MAX_SHELL = 2` (55 sub-cells) is Stage 1's own fixed test
value. Wired into `render.js`'s `init()` as a genuinely separate
`InstancedMesh` (own geometry/material/capacity, never touching
`MAX_CELLS`) demoed on the seed cell at `(0,0,0)`, unconditionally
visible (no camera trigger, per this stage's own scope) — verified live
via Playwright: real orange sub-cells render nested exactly at the seed
cell's location, correctly scaled, tiling with no visible gap/overlap at
both default and close zoom, zero console errors.

**Stage 2 — Camera-Distance Trigger & Lifecycle — DONE, 2026-08-13.**
Wire real camera-distance detection so nearby cells' sub-lattices appear/
dispose as the camera moves, throttled. Verify bounded memory over a long
simulated camera path (no leaked geometry).

Real, deliberate deviation from this stage's own suggested pattern
(`refreshClaims`'s clear-and-rebuild): claims are few, irregularly-shaped,
and each needs its own real convex-hull geometry, so that pattern
allocates/disposes a mesh per claim every recompute. Sub-lattice cells are
many but every one is the exact same shape (one shared geometry per Stage
1) — reused the TOP-LEVEL `mesh`'s own pattern instead (a fixed-capacity
`InstancedMesh` with an adjustable `.count`, never allocating/disposing
after one-time setup), a strictly stronger answer to "no leaked geometry"
than clear-and-rebuild: there is nothing to leak, since nothing is ever
created or destroyed after the initial allocation. `SUB_LATTICE_TRIGGER_
DISTANCE = 4` world units (real-reasoned: the default camera framing sits
~11.2 units from the origin, so 4 keeps the sub-lattice invisible at the
ordinary starting view while comfortably reachable by zooming in, per
this stage's own first success check) and `MAX_NEARBY_SUBLATTICE_CELLS =
20` (bounds worst-case cost independent of world size, same discipline as
`MAX_CELLS`/`MAX_UNDO` elsewhere) are flagged as tunable per section 10's
own open question. `selectNearbyCells` (`latticezoom.js`) is the real,
pure, unit-tested selection logic (Euclidean distance, real scale
factor, closest-first capped at the bound); `render.js`'s `refreshSubLattice`
is pure THREE-specific mesh-buffer wiring on top, self-rescheduled via a
throttled `setTimeout` loop (250ms default) rather than a fixed
`setInterval`, so Stage 4's own adaptive-damping widening can take effect
on the very next tick with no timer teardown needed.

Verified via `node --test` (5 new tests, 148 total) and a real Playwright
run through all three states: default zoom shows a single solid block
(no sub-lattice computed), close zoom reveals the real sub-lattice
nested at the cell's location, and zooming back out makes it disappear
again — zero console errors throughout.

**Stage 3 — Multi-Level Depth & Blending — DONE, 2026-08-13.** Extended to
a real second nested level (`MAX_LOD_DEPTH = 2`) with cross-fade/scale
blending across every threshold crossing, both the base reveal (world
cell → depth-1 sub-lattice) and the recursive one (depth-1 sub-cell →
depth-2 sub-sub-lattice).

`latticezoom.js` grew a general, non-integer-coordinate core
(`generateSubLatticeAt(parentCenter, parentScale, maxShell)`) that
`generateSubLattice` (the original top-level-only call shape) now just
delegates to -- this is what makes recursion possible at all: a depth-1
sub-cell's own real `worldPosition`/`scale` (both already returned per
cell) feeds straight back in as the "parent" for depth 2, zero special-
casing between levels. `selectNearbyByWorldPosition` is the same
generalization for the selection side (`selectNearbyCells` itself
untouched, still used for the top-level/depth-1 case). `levelTriggerDistance`
and `blendFactor` are the two new pure functions Stage 3 actually needed:
a deeper level's trigger distance AND blend width both shrink by the
SAME `subScaleFactor` the geometry itself shrinks by (self-similar reveal
ratio at every depth, not a second unrelated set of numbers per level),
and `blendFactor` is a plain linear ramp (1.0 at/inside the inner
trigger, 0.0 at/beyond `inner + blendWidth`).

`render.js` wiring: a second fixed-capacity `InstancedMesh` (`level2Mesh`,
same "no allocation/disposal after one-time setup" pattern as level 1,
reusing `subLatticeMaterial` unmodified per governing decision 3's
"uniform substructure" -- no new color invented per depth).
`refreshSubLattice` now computes a real blend value per PARENT (using the
`.d` distance `selectNearbyCells`/`selectNearbyByWorldPosition` already
attach to each result) and applies it as a uniform SCALE multiplier to
every sub-cell that parent reveals, via a shared `writeBlendedInstance`
helper -- a whole-parent fade, not each of its own sub-cells dissolving
independently (which would read as the sub-lattice partially melting
rather than the parent smoothly resolving into it). `SUB_LATTICE_BLEND_
WIDTH`/`LEVEL2_BLEND_WIDTH` are grounded as roughly one cell-width of
that level's own geometry (the fade completes over about the distance
the cell itself spans) -- `levelTriggerDistance` reused verbatim for the
depth-2 blend width too, which happens to come out exactly equal to
`level2Scale`, confirming the grounding holds at depth as well as at the
base. `MAX_NEARBY_LEVEL2_PARENTS = 4`: `LEVEL2_TRIGGER_DISTANCE` is
already ~0.26x the depth-1 trigger (`subScaleFactor(2) = cbrt(1/55)`), so
only a small handful of depth-1 cells can ever be that close to the
camera at once -- same "real cap grounded in reasoned cost" discipline
as `MAX_NEARBY_SUBLATTICE_CELLS`.

Verified via `node --test` (6 new tests in `latticezoom.test.mjs` --
delegation parity between `generateSubLattice`/`generateSubLatticeAt`,
real recursion positioning a level-2 sub-lattice at a level-1 cell's own
center rather than the top-level parent's, `selectNearbyByWorldPosition`
parity, `levelTriggerDistance`'s self-similar shrink, `blendFactor`'s
ramp/monotonicity -- 155 total, all passing) and a real Playwright run
(`chromium`, driving actual mouse-wheel zoom over the canvas, not a
hardcoded camera jump): default zoom shows a single solid block; a fine-
grained zoom sequence shows the depth-1 sub-lattice revealing with a
visibly irregular (distance-based, not a flat clipping plane) boundary
as the camera approaches, then genuinely smaller depth-2 facets appearing
nested within it at closer range still -- both confirmed by eye in the
actual screenshots, not inferred from code; zoomed back out, both meshes'
`.count` return to empty (no stuck/leaked geometry); zero console/page
errors throughout. One real gotcha hit while WRITING that Playwright
script, not in `render.js` itself: `#controls`/`#shells-panel` are fixed-
position overlay divs with their own `overflow-y: auto`, so a wheel event
dispatched at the viewport's visual center lands ON the panel and scrolls
IT instead of reaching the canvas/OrbitControls -- the first verification
attempt silently zoomed nothing at all for exactly this reason, caught
only because the "close zoom" screenshot looked identical to the default
one. Fixed by targeting a screen point clear of both panels. Logged in
`.claude/skills/browser-test-harness/SKILL.md` so a future session
driving OrbitControls zoom via Playwright doesn't lose time to the same
thing.

**Stage 4 — Adaptive Damping — DONE, 2026-08-13.** Real volatility-driven
widening of the recompute throttle (section 5), reusing
`RHOMBIVERSE_PRINCIPLES.md` section 2's own generalized shape verbatim --
the exact same one `evolution.js`'s `nextVolatilityScore`/
`VOLATILITY_DECAY_FACTOR` already implements for population swings, not a
new mechanic invented for this spec. `latticezoom.js` gained the pure
side: `swingMagnitude(movement, triggerDistance)` normalizes real
reference-position movement between refreshes by the base trigger
distance (the same "normalize by something already real in the system"
shape `evolution.js`'s own swing check uses, there normalizing by prior
population); `nextVolatilityScore(currentScore, movement, triggerDistance)`
mirrors `evolution.js`'s own function shape exactly -- accumulate the
magnitude on a real swing (`SUB_LATTICE_SWING_FRACTION_THRESHOLD = 0.3`,
the same literal threshold VALUE `evolution.js` uses, adapted to this
domain), multiplicatively decay otherwise
(`SUB_LATTICE_VOLATILITY_DECAY_FACTOR = 0.9`, same value and role as
`evolution.js`'s own decay factor); `throttleForVolatility(volatilityScore)`
maps the score onto the real interval `render.js`'s self-rescheduling
timer should use next, linearly widening from `SUB_LATTICE_THROTTLE_
BASE_MS` (250, the pre-existing Stage 2 tight default, now named) up to a
bounded `SUB_LATTICE_THROTTLE_MAX_MS` (1000 -- even under sustained rapid
scrubbing, a recompute still happens at least once a second, so the
revealed sub-lattice never lags the camera by more than that) at a rate
(`SUB_LATTICE_THROTTLE_MS_PER_VOLATILITY = 150`) reasoned so reaching the
cap requires roughly five consecutive full-strength swings with no
intervening calm tick -- genuinely sustained scrubbing, not one flick of
the wheel.

`render.js`'s `refreshSubLattice` tracks `lastSubLatticeRefPos` and
computes real movement since the previous refresh at the top of every
call, feeding it through `nextVolatilityScore` to update
`subLatticeVolatilityScore`, then `throttleForVolatility` to update
`subLatticeThrottleMs` -- the pre-existing self-rescheduling `setTimeout`
loop (built this way back in Stage 2 specifically so this would need no
changes) picks up the widened/narrowed value on its very next scheduling
call automatically.

Verified via `node --test` (7 new tests in `latticezoom.test.mjs` --
`swingMagnitude`'s normalization and zero-trigger-distance guard,
`nextVolatilityScore`'s real accumulate-vs-decay branches and multi-tick
divergence between sustained rapid and sustained calm sequences,
`throttleForVolatility`'s monotonic widening bounded at the cap, and a
literal "scripted rapid-zoom vs calm-movement control" test matching this
stage's own build-order success check verbatim -- 162 total, all
passing) AND a real Playwright run against the actual `render.js` wiring
(not just the pure functions): a temporary `window.__scratchSubLatticeDebug()`
hook (added for this one verification run, removed again immediately
after -- `render.js` itself carries no permanent debug surface, same as
every prior stage) confirmed a real scripted rapid-scrub sequence widens
the live throttle to the 1000ms cap (`volatilityScore` reaching ~5-9 in
the process) while a calm control stays exactly at the 250ms base, and
that the throttle genuinely decays back down again during a real held-
still period afterward -- settling, not a one-way ratchet, confirming
section 2's own "not infinite... genuine settling" requirement holds in
the actual running app, not just in the isolated math. One real,
non-obvious behavior surfaced only by this live run, not by reading the
code: while throttled near the cap, refreshes (and therefore decay ticks,
which only fire once per refresh) happen only about once a second, so
wall-clock recovery time after a big scrubbing burst is itself
proportionally longer right after the burst -- a genuine emergent
consequence of the throttle interval and the decay mechanism sharing the
same tick, not a bug; the verification script had to poll for the decay
rather than assume a fixed wait would be long enough, and that fixed-wait
version genuinely failed on the first run before being corrected.

**Stage 5 — Ecosystem Rendering (Real Organisms + Plant-Coverage Layer) —
DONE, 2026-08-13.**

Real design call made re-reading section 6.1's own text closely before
building anything (not guessed, not asked either -- the text itself
resolves it): "an organism is just more content that becomes visible
once the camera is close enough for its actual (tiny) size to register
at all" describes REPLACING an organism's existing always-visible,
wrong-scale rendering with this stage's LOD-gated tiny version, not
adding a second copy alongside the old one -- that always-visible
rendering (Evolution Stage 9's own real, tested, shipped feature) WAS
the literal "scale-mismatch problem the project owner raised" this
section opens with (an amoeba/plant rendered via the same growth-tile
pipeline as ordinary Penrose-growth content, at the same order of
magnitude as a whole building block). `render.js`'s `rebuildSeedMeshes`
now returns early (after clearing any stale mesh entry) for any seed
whose `species` carries `evolution.js`'s own `ORGANISM_SEED_SPECIES_
PREFIX` -- ordinary (non-organism) growth species are completely
unaffected, still rendered exactly as before.

**Tier 1 (a few real organisms, section 6.1):** a new `organismMiniGroup`
(clear-and-rebuild `THREE.Group`, the SAME pattern `refreshClaims` already
uses for "few, irregularly-shaped, real-hull-per-item" content -- not the
sub-lattice's own many-identical-instances InstancedMesh shape, a
deliberately different reuse than Stage 3/4's own). Every refresh, the
closest `MAX_NEARBY_ORGANISMS` (20) real tracked organisms to the
reference position (via `selectNearbyByWorldPosition` on each organism's
own real seed origin, the exact same selection core Stage 3's recursion
already uses) get their own EXISTING, already-correct growth-tile
geometry (`tileWorldVertices`) reused outright -- just scaled DOWN around
the organism's own real rooted position (`scaleVerticesAroundOrigin`,
new pure helper) by the SAME ratio depth-1 sub-lattice cells shrink by
(`subScaleFactor(SUB_LATTICE_MAX_SHELL)`), times that organism's own
real distance-driven `blendFactor` -- so it fades in/out exactly like
every other Lattice Zoom reveal, no separately-tuned fade. Organisms
whose blend has decayed to exactly 0 are skipped rather than building a
degenerate (every-vertex-collapsed-to-a-point) `ConvexGeometry`.

**Tier 2 (aggregate/plant-coverage layer, section 6.1):** NOT
independently tracked per instance, per section 6.1's own explicit
governing decision -- section 10's own "leaning toward instanced
geometry... for a first pass" is what got built: a new fixed-capacity

"Resolved through the SAME deterministic catch-up shape as Evolution
Stage 4" is the spec's own instruction, taken literally: `landscapeState`
is one more field on the EXACT SAME `planetoidEvolution` record

loop -- grounded directly in section 6.2's own text ("real landscapes are

## 10. Open Design Questions (flagged, not blocking)

- Exact `SUB_SCALE_FACTOR` and shell count per sub-lattice — needs real
  geometric derivation during Stage 1, not fixed here.
- Exact `MAX_LOD_DEPTH` and per-level trigger distances — needs real
  frame-cost measurement during Stage 2/3, not guessed here.
- Whether sub-lattice cells carry any material/rendering variation at all
  in this pass, or are purely the parent cell's own material repeated
  (leaning toward the latter, matching governing decision 3's "uniform
  substructure" — not fixed here).
- How Walk Mode's own player-collision/movement interacts with visible
  sub-lattice detail (does a player's collision volume ever interact with
  sub-cells, or do they stay purely visual against the existing
  block-level collision the whole time this pass lasts) — leaning toward
  "purely visual, block-level collision unchanged," matching governing
  decision 4, but worth confirming explicitly before Stage 2.
- Exact formula mapping aggregate population stats (coverage %, dominant
  traits) onto the aggregate landscape layer's own visual density/look —
  needs a real pass once Evolution Stage 5's `biomass` figure actually
  exists to read from (section 6), not fixed here.
- Whether the aggregate layer uses real instanced geometry (cheaper,
  cruder) or a shader/texture-based technique (richer, more engineering)
  — leaning toward instanced geometry for a first pass, matching this
  whole spec's "no build step, reuse existing patterns" discipline, but
  not fixed here.
- Future wave (explicitly out of scope here, per the project owner's own
  framing): sub-scale interactivity — building/mining at the revealed
  detail level, once a "more rendered approach" exists to support it.
